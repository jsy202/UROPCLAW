# 필터 제안과 검증 과정

이 기록은 실제 구현·관측·수정한 내용을 담는다. 최종 구성은 결과를 확인한 뒤 정하며, 기대했던 이득을 관측된 효과처럼 쓰지 않는다.

## 1. 개선을 쌓는 방식으로 비교를 구성함

모든 검출 후보를 고비용 검증으로 보내는 기준에서 시작해 HSV 색상 선별과 대상별 중복 억제를 차례로 추가한다. 그다음 순간 색상 오판을 줄이려는 연속 확인을 추가해 요청 절감과 목표 손실·확인 지연을 함께 비교한다. 필터 유무의 전체 조합과 색상 처리 배치 대안은 보조 비교로 남긴다.

이것은 구성의 효과를 설명하는 실험 순서다. 과거에 실제로 이 순서대로 개발했다는 이력을 만들어내지는 않는다. 추적은 모든 구성에서 공통으로 사용하며, 연속 확인을 켰을 때 실제 처리는 추적 → 연속 확인 → 목표 색 gate → 중복 억제다.

## 2. ‘3프레임’의 실제 의미를 먼저 확인함

기존 모듈은 같은 track의 관측 세 개를 모아 unknown을 제외한 색상 투표를 한다. 세 번 모두 목표 색이어야 하는 규칙도, 최근 세 관측을 계속 갱신하는 규칙도 아니다. 판정 후 기록을 비우며 관측 간격이 1초를 넘으면 초기화한다.

따라서 N=1/2/3/5/7/10의 관측 수 비교와 전체 분모·만장일치·슬라이딩 투표 규칙 비교를 나눴다. 기존 규칙과 재생 구현의 일치는 별도 테스트로 확인했다. 짧은 출현에서 관측 수를 채우기 전에 사라지는 문제를 평가에서 숨기지 않도록 누락과 성공 조건부 지연을 함께 보고한다.

## 3. 녹화 길이를 원래 기준과 맞춰 다시 수집함

초기 비교는 10Hz · 180초 · 1,800장인 녹화 40개로 진행했다. 사용자는 원래 기준과 같은 실행당 6,000장을 요청했다. 원래 저장소의 세계 tick이 0.1초라는 것을 확인하고, 최종 조건을 10Hz · 600초 · 6,000장으로 확정했다. 제안 중 언급된 5Hz · 20분 수집은 실행하지 않았다.

기존 자료를 이어 붙이지 않고 새로 수집했다. 처음에는 40개를 계획했으나 사용자가 30번째 녹화까지만 수집하도록 범위를 줄였다. Town10HD_Opt의 3환경 × 2밀도 × 5seed로 끝내며 두 번째 지도는 추가하지 않는다. 초기 72,000장은 탐색 자료로 따로 보존하고 새 180,000장 집계에 섞지 않는다. 평가 결과를 보고 표본을 줄인 것은 아니며, 선택 기준은 그대로 유지한다. 완료 검사는 6,000개의 연속 index·센서 frame·시각, 이미지 존재, actor 정리 성공을 확인한다. 이전 1,800장 검사도 유지해 과거 결과를 재현할 수 있게 했다.

## 4. 같은 영상으로 비교하되 재추론 차이를 없앰

각 원본 센서 프레임에서 YOLO와 HSV를 한 번만 계산해 저장한다. 28개 구성은 그 캐시와 시뮬레이션 시각을 공유하되 추적·투표·중복 억제 상태는 따로 가진다. GT actor ID는 평가에만 주고 필터에는 전달하지 않는다.

JPEG를 다시 추론하면 압축과 반복 실행의 영향이 섞일 수 있어 저장 JPEG는 장면 확인용으로 쓴다. 따라서 ‘저장 이미지로 비교한다’는 설명은 정확히는 같은 녹화에서 얻은 동일 검출·색상 캐시를 재생한다는 뜻이다. 이미지별 해시와 녹화별 manifest·JSONL 해시로 원자료를 확인한다.

## 5. 배치 대안이 이미 색상 정보를 받는 오류를 수정함

초기 대안 구현에서 ‘추적 후 색상 판별’ 구성의 추적기에 원래 색상 라벨이 들어가는 것을 테스트로 발견했다. 이 상태에서는 색상 처리 위치를 뒤로 옮겨도 추적의 재연결 판단에 색상이 먼저 쓰인다.

해당 대안에는 추적 입력으로 unknown만 전달하도록 수정했다. 재생 시각을 공유 모듈에 주입할 때는 finally로 원래 시계를 복구한다. 이번 비교에는 수정된 구현을 사용한다. 배치 대안은 단순 연산 순서뿐 아니라 추적의 색상 정보 사용도 바꾸므로 그 효과를 순수한 순서 효과라고 부르지 않는다.

## 6. 지도 전환과 남은 서버 자식 프로세스를 처리함

초기 수집 중 비최적화 Town03 로딩에서 native 충돌이 발생했다. Opt 지도는 로딩됐지만 실행 인자만으로 요청한 지도가 적용됐다고 가정할 수 없었다. RPC로 지도를 로드하고 실제 이름을 검사하도록 바꿨다. 비최적화 지도 충돌의 내부 원인까지 해결했다고 주장하지 않는다.

서버 wrapper 종료 후 Unreal 자식이 남아 포트를 점유한 문제도 있었다. 소유한 프로세스 그룹을 정리하고 포트 해제를 확인하도록 수정했다. 이번 수집기는 이 경로를 사용하며, 자신이 시작하지 않은 CARLA 서버가 있으면 종료하지 않고 중단한다.

## 7. 개발 선택과 평가 검증을 구분함

개발 12개에서 N1 대비 목표 출현 도달 손실 2%p 이내, 확인 지연 p95 0.5초 이내인 설정을 고른다. 이 안에서 비목표·미연결 요청, 전체 요청, 작은 N 순으로 선택하고 선택 파일을 고정한 뒤 평가 18개를 분석한다.

평가 결과를 보고 N을 다시 골라 처음부터 그 설정을 선택했던 것처럼 서술하지 않는다. 연속 확인을 유지할 사전 기준을 입증하지 못하면 추가 후 검증을 거쳐 제외한 시행착오로 기록한다. 기준 미충족과 ‘어떤 조건에서도 효과가 전혀 없음’은 구분한다. 최종 판단과 실제 수치는 [결과 보고서](REPORT.ko.md)에 연결한다.

## 8. 실제 VLM을 비교에서 제외함

사용자 지시 이후 실제 VLM·알림은 실행하지 않는다. 초기 지시 이전에 실행한 연결 확인 1건은 본 비교에서 제외했다. 이번 새 수집·재생은 실제 VLM 호출이 없으며, 보고하는 요청 수는 VLM을 요청했을 트리거 수다. 필터 지연을 VLM 응답 시간이나 최종 경보 시간으로 해석하지 않는다.

## 최종 관측과 결정

30개 녹화와 180,000장의 저장·무결성 검증을 완료했다. 수집 범위 변경 때 다음 작업으로 넘어가는 supervisor만 대기시키고 진행 중인 녹화는 끝까지 저장했다. 30번째 완료와 actor 정리를 확인한 뒤 소유 서버를 종료했으며, 31번째 디렉터리는 만들지 않았다.

개발 12개에서는 N1이 선택됐다. 평가 18개에서 HSV와 대상별 중복 억제를 차례로 추가하면 요청이 156,109→6,088→363회로 줄었다. 동시에 목표 출현은 309→294→276건, 고유 차량은 105→104→102대로 줄었다. 비용 절감만으로 무손실 개선이라고 쓰지 않았다.

N3를 추가하면 요청은 294회로 줄었지만 목표 출현은 232/309, 고유 차량은 99/105였고 확인 지연 p95는 0.70초였다. 요청 절감과 비목표·미연결 요청 감소는 실제 이득으로 남기되, 사전 목표 손실·지연 기준을 충족하지 못해 최종 구성에서 제외한 시행착오로 분류했다. N2의 고유 차량 도달은 102/105로 N1과 같아 다른 목표 아래의 교환 관계를 인정했다. 평가 뒤 목표나 개발 선택을 바꾸지는 않았다.

배치 대안은 출현 도달 수가 같았지만 고유 차량·요청·지연에 작은 차이가 있었다. 기존 배치의 유일한 우월성을 주장하지 않고, 현재 정보 의존 관계를 유지하는 구성을 이번 운영 기준의 권장안으로 남겼다. [최종 요약](SUMMARY.ko.md)에 수치와 한계를 함께 기록했다.
